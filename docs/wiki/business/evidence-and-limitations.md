# 证据口径与风险限制

> 面向需要决定“是否试点 Maglev、试点如何验收”的业务负责人和技术负责人。本页不替你给出收益数字，而是提供一套可以在具体项目中复核的评估方法。

这套 Wiki 以 `internal Reality/` 的当前事实为锚点。页面可以帮助读者定位事实、静态契约和已知缺口，但页面本身不把设计存在写成运行效果，也不替代项目现场验证。

## 先明确评估对象

Maglev 不是编码工具的替代品，而是编码工具的上游输入层和下游验证层：

- 上游：把需求、边界、方案和完成标准整理成更稳定的输入；
- 执行中：让上下文、角色和规则有可追踪的交接；
- 下游：检查需求、方案、代码和测试之间是否仍然一致；
- 长期：把已经验证的事实和决策沉淀到后续协作可以继续使用的位置。

因此，试点评估不应只问“AI 写代码快了多少”，还要问：团队是否更容易形成共同理解，偏差是否更早被发现，结果是否能被下一次任务复用。

## 证据状态：什么已经知道，什么还不知道

| 判断 | 含义 | 可以怎么用 | 不能怎么用 |
|---|---|---|---|
| 当前事实 | Reality、实现或正式指南中有明确来源的内容 | 作为项目检查和接入决策的起点 | 不能自动推导组织收益 |
| 静态契约 | 文件、字段、接口、路径或状态规则已经登记 | 验证输入输出和责任边界 | 不能代替运行验证 |
| 已知缺口 | 来源明确列出尚未证明、未覆盖或需要人工判断的部分 | 纳入风险登记和验证计划 | 不能用页面措辞掩盖 |
| 未知 | 当前来源不足以支持结论 | 保留为 unknown 或 blocked | 不能用常识补齐 |

“有页面”“有配置”“有命令”只能说明静态资产存在。它们不能单独证明运行拓扑、端到端成功率、用户体验、跨环境兼容性或组织级收益。

## 建立一个可复核的试点评估

### 1. 先记录基线

在引入 Maglev 前，先记录同类任务的实际情况。不要只记录平均耗时，还要记录造成返工和争议的原因：

- 从需求确认到可验收结果的时间；
- 需求、设计、实现和测试之间出现过多少次口径修正；
- 返工来自需求不清、上下文缺失、实现错误还是验收标准不一致；
- 新成员或新会话重新理解模块需要哪些材料；
- 哪些结果只能依赖熟人解释，无法通过仓库材料复核。

基线的作用是说明比较对象是什么，不是预先承诺目标数字。

### 2. 选择一条真实、可封闭的变更

选择一个边界清晰、能够在有限范围内完成验证的任务。适合的样本通常包括：

- 有明确输入、状态和验收标准的业务变更；
- 存量项目中一个真实热点模块的局部修改；
- 同时涉及需求、设计、代码和测试对齐的小型流程变更。

不适合一开始就用整个仓库重构、跨多个外部系统的开放任务或没有明确完成标准的探索性项目作为唯一样本。

### 3. 预先定义观察指标

指标应由团队在试点前决定，并说明采集方式和边界。可以观察：

| 观察面 | 示例问题 |
|---|---|
| 对齐质量 | 需求、方案、代码和测试是否描述同一件事？ |
| 返工 | 哪些偏差在实施前、实施中、验证阶段被发现？ |
| 交接 | 下一位执行者能否仅凭仓库材料继续工作？ |
| 可复用性 | 本次形成的 Spec、验证依据和当前事实能否服务下一次任务？ |
| 操作成本 | 初始化、上下文准备、审查和维护分别增加了什么工作？ |
| 风险暴露 | 哪些未知、权限、数据或兼容性问题被提前发现？ |

不要预先把“AI 生成代码行数”“固定倍数提效”或单个成功案例当作充分指标。代码行数不是价值，单次成功也不是稳定能力。

### 4. 设计对照和验收

如果要比较不同工作方式，至少保持以下条件可解释：

1. 任务边界和输入材料相同；
2. 验收标准在执行前冻结；
3. 记录人工投入、返工、缺陷和等待时间，而不是只记录完成时间；
4. 由与实施者不同的人或角色执行最终验收；
5. 把未完成、阻断和无法比较的结果保留下来。

试点结论应写成“在这个任务、这个团队、这个工具链和这个时间窗口内观察到什么”。不能从一次局部比较外推到所有组织或所有编码工具。

## 成本与风险不能省略

采用评估至少需要正视四类成本：

- **学习成本**：团队需要理解新的入口、Spec、索引和验证动作；
- **维护成本**：当前事实、索引、页面和发行物需要持续刷新；
- **集成成本**：现有 IDE、Agent、CLI、扩展和权限边界需要逐项核对；
- **组织成本**：需求、技术实施、体验和验证责任需要明确交接。

还要检查：

- Spec 或代码是否包含不能进入所用模型的数据；
- 存量接入是否可能影响业务连续性；
- 团队是否有人能裁决业务边界和验证结果；
- 失败时是否存在人工兜底，而不是只能依赖自动流程。

## 不能从 Wiki 推断的内容

- 组织导入后必然减少多少时间、成本或返工；
- 所有 Agent、IDE、扩展和部署环境都能无配置组合；
- 静态主链图等于每次运行都会按同样顺序成功；
- 一个团队的试点结果可以直接推广到另一种项目形态；
- 当前页面没有列出的能力不存在，或已列出的能力在所有项目中都可用。

## 评估结论格式

建议每次试点结束后保留以下结构：

```text
样本范围：
基线事实：
观察到的变化：
已被验证的结论：
仍然未知或阻断的结论：
成本与风险：
是否扩大范围：是 / 否 / 需要补充证据
```
