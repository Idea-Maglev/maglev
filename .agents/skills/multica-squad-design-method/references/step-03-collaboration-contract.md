# Step 3: Collaboration Contract

## 目标

让小队通过明确协议协作，而不是依赖成员“读懂上下文”的聊天默契。

## 必须写入的协议点

1. 协调/路由责任角色是唯一默认路由者，具体名称由小队配置决定。
2. 协调/路由责任角色每轮只委派一个主责任角色；只有明确的只读并行审查例外才可追加目标。
3. 委派必须使用 Squad Roster 中的精确 mention markdown：`[@名称](mention://agent/<uuid>)`。
4. 必须发布新评论触发，不得编辑旧评论补 mention。
5. 不得使用裸 `@name`。
6. 成员只响应属于自己的新委派 Task。
7. 成员完成、阻塞或失败时必须发布标准终态 Handoff。
8. 成员默认交回协调/路由责任角色评估。
9. 成员不得横向互相委派。
10. 只有协调/路由责任角色的委派评论明确授权“一次性只读并行审查”时，成员才可以 mention 指定协作者。
11. 自动接力失败时按顺序检查：
    - 目标 Agent 是否在当前承载中可调用。
    - 执行运行时是否在线。
    - mention markdown 是否为 `mention://agent/<uuid>` 或 `mention://squad/<uuid>` 精确格式。
    - 评论是否为新建评论而不是编辑旧评论。

## 共享上下文与有限调度

- 跨隔离环境交接的产物必须携带不可变版本标识，并由接收方完成上下文准入。
- 本地未提交、未同步或接收方不可回查的版本不能进入后续业务动作。
- 协调/路由责任角色消费 Handoff、当前状态和证据时必须形成决策指纹；同一指纹没有新增证据时不得重复派发。
- 没有合法下一责任目标时只给出一次性 `human_action`、`blocked` 或 `awaiting_external`；满足完成条件时使用 `ready_to_close` 停止普通派发。

## 人类责任路由

- 需要人类动作时先选择角色，再依据角色内成员描述和顺序选择成员。
- 描述无法唯一匹配时选择第一顺位并记录兜底；一个成员可以承担多个角色，一次 Handoff 可以指派多个角色。
- 没有人类动作时允许 `human_targets: []`；身份、责任承载和通知结果必须由实际承载回执证明。

## 通用标准 Handoff

```markdown
## Multica 小队 Handoff

- 状态：completed / blocked / failed
- 当前角色：
- 当前阶段：
- 输入证据：
- 输出产物：
- 事实结论：
- 推断结论：
- 未知项：
- 是否修改外部状态：
- 修改范围：
- 基线：
- 验证命令或验证动作：
- 阻塞原因：
- 下一建议责任人：
- 是否需要负责人确认：
```

## Handoff 规则

- `状态` 必须三选一：`completed` / `blocked` / `failed`。
- 有证据的内容进入“事实结论”；没有证据的内容进入“推断结论”或“未知项”。
- 成员只能提出“下一建议责任人”，不能把它当成已委派任务。
- 如修改了外部状态，必须写明修改范围、基线和验证动作。

## 状态意图和外部回执

- `status_intent` 只能表达受限的状态转移意图，不能代替实际状态结果。
- 只有收到关联任务、触发原因、前后状态和回执引用后，才能记录外部状态已更新。
- 缺少回执时保持 `unverified`，并转为 `blocked`、`awaiting_external` 或一次性 `human_action`。

## 审查、反馈和复审

- 审查角色只读追溯实际生产者 skill 的既有标准、格式和来源，不要求生产者 skill 增加新接口。
- Review Packet 至少包含标准来源、共享阶段门槛、事实证据、影响、修复建议、目标责任角色、阻塞条件和复审要求。
- 协调/路由责任角色只选择一个主修复角色；修复产生新产物、Handoff 和验证证据后，由独立角色复审，复审前不能标记 `resolved`。

## 输出

- 协同协议段落。
- Handoff 格式。
- 横向委派边界。
- 自动接力失败排查顺序。
